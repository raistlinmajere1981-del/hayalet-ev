1) Overall assessment

The repository has a strong i18n foundation (central catalogs, renderer helpers, language packs), but it is not yet production-grade for multilingual consistency because several user-visible paths still bypass i18n and can leak mixed-language/system messages. The most critical risks are:

    Hardcoded UI text still present (not key-based).

    Raw backend error messages shown directly in UI (language can vary by source).

    Fallback strategy leaks translation keys when keys are missing.

    Language sync gap in preload (locale is loaded once, not kept in sync).

    Namespace/key centralization is partially implicit (runtime log-key merging + auto-prefixing), which hides inconsistencies and makes regressions easier.

2) Missing i18n coverage by module/page
A) src/js/pages/opencode-ui (chat empty state)

    Title: Hardcoded welcome subtitle in Turkish-like text

    File path: src/js/pages/opencode-ui/host-helpers.ts

    Severity: High

    Confidence: High

    Why it matters: This is directly visible in chat empty state and ignores selected app language.

    Exact problem: subtitleEl.textContent = "Hos geldin. Bugun ne yapmak istersin?";

    Exact fix direction: Move to opencodeUi.* translation key (e.g. opencodeUi.chat.emptySubtitle) and render via t(...).

B) src/js/pages/server

    Title: Server command result panel renders raw backend message

    File path: src/js/pages/server.ts

    Severity: Critical

    Confidence: High

    Why it matters: Command detail panel can show non-localized mixed strings from different backend modules.

    Exact problem: result.message / result.detail is preferred over localized fallback and inserted into UI text area.

    Exact fix direction: Introduce message codes from backend, map codes to i18n keys in renderer; only include raw detail as secondary diagnostic suffix.

C) src/js/pages/archives

    Title: Archive status messages can expose raw backend error text

    File path: src/js/pages/archives/actions.ts

    Severity: Critical

    Confidence: High

    Why it matters: User-facing status line can show untranslated or mixed language DB/Electron errors.

    Exact problem: ctx.setStatus(result?.error ?? ... ) used in delete and save flows.

    Exact fix direction: Standardize IPC response to { code, detail }; map code to localized text and append normalized detail via formatErrorWithDetail.

D) src/js/pages/archives/protocol-editor

    Title: Protocol save success path can show backend raw message

    File path: src/js/pages/archives/protocol-editor.ts

    Severity: Medium

    Confidence: High

    Why it matters: Success/error status can bypass consistent i18n tone and language.

    Exact problem: For success, message: result.message is returned directly.

    Exact fix direction: Return standardized success code and localized renderer message; keep raw backend detail for logs only.

3) Hardcoded user-facing strings by file
A) src/js/pages/opencode-ui/host-helpers.ts

    Hardcoded subtitle string in UI.

B) electron/command-manager.ts

    Hardcoded mixed-language backend errors ("jobId eksik", "Parameters are missing", "Source directory is missing"), which can surface in renderer detail/status flows.

C) electron/device-manager.ts

    Hardcoded English error messages ("Device actions supported on Linux only", "key missing", "text missing", "xclip not installed"), potentially surfaced to user-facing flows.

4) Inconsistent key usage / duplicate key patterns
A) Runtime namespace normalization hides key-ownership inconsistency

    Title: app.logs and shell.logs are merged at runtime

    File path: shared/i18n/catalog.ts

    Severity: High

    Confidence: High

    Why it matters: Different modules can reference different namespaces for similar keys; mistakes are masked until tooling/static audits fail.

    Exact problem: normalizeLogNamespaceCatalog rewrites both app.logs and shell.logs to a merged canonical map.

    Exact fix direction: Choose one canonical namespace (shell.logs or app.logs), migrate all call sites + catalogs, then remove merge shim (or keep temporarily with deprecation warnings).

B) Auto-prefixing in shellT can hide wrong key roots

    Title: Implicit shell. prefixing reduces explicitness

    File path: src/js/app/shell-i18n.ts

    Severity: Medium

    Confidence: High

    Why it matters: A mistyped root can silently resolve to another namespace path, making audits and consistency harder.

    Exact problem: Keys without root in ROOT_NAMESPACES are auto-prefixed to shell.*.

    Exact fix direction: Prefer explicit full keys in critical UI paths; add lint rule to forbid implicit prefix usage for new code.

C) Preload/webviewPreload translations duplicated in both locale files as bilingual subobjects

    Title: Locale catalogs contain embedded en/tr subkeys for preload domains

    File path: shared/languages/en/index.json, shared/languages/tr/index.json

    Severity: Medium

    Confidence: High

    Why it matters: This is structurally different from the rest of catalog and increases maintenance drift risk.

    Exact problem: Keys under electron.preload.* and electron.webviewPreload.* are objects with both en and tr in both files.

    Exact fix direction: Prefer normal locale split (each locale file stores only its own string); keep preload resolver simple and consistent with global i18n model.

5) Fallback and language-sync risks
A) Missing key fallback leaks raw key token

    Title: Fallback behavior returns key string directly

    File path: shared/i18n/catalog.ts

    Severity: High

    Confidence: High

    Why it matters: End users may see internal key paths instead of message text in edge cases.

    Exact problem: translateCatalog(...) returns key when template not found.

    Exact fix direction: Return localized generic fallback (common.translationMissing) and log telemetry with missing key details.

B) Preload locale is initialized once, no visible ongoing sync path

    Title: Preload language may become stale after runtime language change

    File path: electron/preload.cjs

    Severity: High

    Confidence: Medium-High

    Why it matters: Renderer can change language while preload-origin messages remain old locale.

    Exact problem: syncPreloadLocale() runs at startup; no explicit subscription/update hook shown.

    Exact fix direction: Add IPC event listener for settings/language changes (or re-sync on relevant actions) and refresh cached preload catalog.

6) Production-critical multilingual issues

    Raw backend message propagation to UI (server + archives).
    This can produce mixed Turkish/English/system text in front-facing status/detail surfaces.

    Hardcoded visible subtitle in opencode-ui.
    Immediate language inconsistency for all non-matching locales.

    Fallback showing translation keys.
    If a key is missing, user gets internal key path instead of usable text.

    Preload locale staleness risk.
    Cross-layer language mismatch possible between renderer and preload-originated strings.

7) Recommended cleanup plan (priority order)
P0 (blocker)

    Stop rendering raw backend messages directly in UI (server panel, archives status).

        Add standardized code-based IPC result contract.

        Map codes to i18n keys in renderer.

        Keep raw detail in logs/expandable diagnostics only.

    Replace hardcoded UI text in opencode-ui empty state with i18n key.

P1

    Change missing-key fallback behavior to user-safe generic text + telemetry.

    Add preload language resync mechanism on settings/language update event.

P2

    Unify namespace strategy for logs (app.logs vs shell.logs) and reduce hidden aliasing.

    Normalize electron preload translation structure to standard locale-per-file model, avoiding embedded bilingual objects in each locale file.
