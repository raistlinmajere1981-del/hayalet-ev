# [INFO][GAME-ROOM][YAHTZEE][US1-TRANSPORT]

This document describes the current direct US1 transport used by Game Room Yahtzee.

## Scope

US1 Yahtzee is a two-player match between the local Game Room seat and the connected US1 remote user. The current slice uses direct connected-room synchronization; it does not add a separate invite/accept screen.

## Host authority

- Each side treats Game Room host state as the gameplay authority for the locally executed command.
- Dice results are generated by the host, never by a transport message or remote UI.
- A synchronized snapshot carries match state only after a valid local host action.
- Score cards, active seat, dice, held flags and roll count are mirrored through transport.

## Commands

The transport uses three room commands:

- `GameRoomYahtzeeRemoteStart` — creates the mirrored side of a new US1 match.
- `GameRoomYahtzeeRemoteSync` — applies a newer match revision.
- `GameRoomYahtzeeRemoteReset` — resets the matching remote game.

Room commands are carried through SlotBridge/US1 room transport rather than interpreted from free-form text.

## Match identity and ordering

Every live remote match has a `matchId` and monotonically increasing `revision`.

A sync is accepted only when:

- the active local state is a US1 Yahtzee match,
- `matchId` matches the active match,
- the incoming revision is newer than the local revision,
- a supplied remote user identity does not conflict with the active remote user.

Older or duplicate revisions are rejected as stale.

## Snapshot contents

The synchronized snapshot contains the data needed to mirror the game, including:

- schema version,
- `matchId` and `revision`,
- active/complete state,
- both player score cards,
- active player/seat,
- `turnIndex` and `turnToken`,
- dice values,
- held flags,
- roll count,
- result/winner state,
- status.

The receiving host normalizes the snapshot before saving it.

## Current limitation

The local user starts the direct US1 match in the current implementation. If a later slice adds invitation UX or selectable starter rules, those should remain transport concerns around the same host-owned game state rather than moving authority into message text.
