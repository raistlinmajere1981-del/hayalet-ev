# Gaia project storage v1

The room-UI commands use the invoking webview's partition and top-level document. The host dispatches the request ID through SlotBridge. The preload retains the payload until dispatch and submits it from that webview. The application build supplies the trusted provider.

- GaiaProjects lists project IDs.
- GaiaCreate accepts project, fixture and locale. The room supplies `layout: "site"` for an empty standard project or the full site fixture. The original request shape still uses the prior starter model. Creation never replaces a saved world.
- GaiaOpen accepts project and an optional building ID. An explicit building must have a floor. Without a building, the response identifies the first editable building if one exists, and always issues a project session.
- GaiaSave accepts batch and retry. Both site and interior batches carry project, session, baseRevision, operationId and edits. An interior batch carries the authorized building ID. A site batch carries `scope: "site"`. A reference batch carries `scope: "reference"` and one edit with `op` set to `import`, `replace`, `appearance`, `calibrate` or `remove`. Success returns the committed world. An exact replay can recover the last successful receipt. A different successful edit supersedes it. Reopen to resolve an older unknown result.

- GaiaReference accepts project, session and a linked asset ID. It returns a bounded, reproducible raster preview for the active webview session.
- GaiaStatus accepts project, session and an optional update. A link update carries kind `link`, deviceId and state `online` or `offline`. An observation carries kind `observation`, deviceId, capability, Unix time in milliseconds, quality, value and unit. Invalid observations carry a null value. The room UI can update virtual devices. The trusted provider fixes the source as `simulated` and returns the latest active `statuses` and the saved world `revision` used to resolve them.

The site batch supports adding a site, building, floor, mount or utility line, binding a virtual device, setting the boundary, building pose and dimensions, floor elevation, mount position and path vertices, reparenting and explicit removal. Building transforms carry the local frames of descendants. Reparenting requires a choice of world or local pose preservation. Path vertices remain in the path's own frame. Removal names every removed node and detached device and rejects surviving parent, zone and reference dependencies. Detached devices remain in inventory under their original IDs. Device edits use `createDevice`, `updateDevice`, `mountDevice` or `deleteDevice`. Device removal carries the expected mount and hardware identity, or null for each absent relationship. Mount placement and linking can be submitted together. The same point can host multiple devices.

New image assets keep their original bytes, detected format, original pixel dimensions and SHA-256. Import and replacement send bytes as base64 and supply fresh asset IDs. A new asset is published before the world and receipt are atomically replaced. The writer retires the previous asset after publication when its last reference is gone. No client supplies a disk path.

A reference can use project coordinates or a site, building, floor or zone frame. Rebinding preserves the world placement of a calibrated image. Replacing the image clears its calibration. The placement lock must be released before calibration, rebinding, replacement or removal. Visibility and opacity can still be changed. Geometry edits and reference edits keep their own scope.

A missing or damaged image is reported alongside the world and retains its reference record. A damaged world cannot be opened. The provider stores one latest connection state and observation per declared capability in `device-status.json`. The latest status can be read after reopening the project and observation updates do not change the world revision. The optional `statusEpoch` in the trusted world document advances on device identity or capability-set changes. The schemaVersion 2 status sidecar binds its inventory digest to this epoch. After a successful world publication, the sidecar is reconciled; if reconciliation is missed, mismatched data fails closed even when an inventory returns to its earlier shape. Valid legacy v1 status data is not reused; new updates write v2. Unreadable sidecars are preserved and status reads fail without blocking world opens or saves. Temporary spatial measurements live in the UI session. OpenPlan3D receives the active floor’s projected underlays as ephemeral render inputs.
